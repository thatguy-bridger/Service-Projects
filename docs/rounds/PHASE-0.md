# Phase 0 — Foundation and the role migration

Status: **built and verified**, on branch `rounds/phase-0-foundation` (off `claude/repo-file-structure-s5g9ro`).

This doc is the record SPEC.md §21 asks every phase to leave behind: what
was built, what was stubbed, what got decided without waiting for a
go-ahead (because the session was unattended — see
`docs/rounds/OPEN-QUESTIONS.md` for everything that needs a real answer).

It also folds in the deliverable SPEC.md §1's master prompt asks for

building and verifying it for real was more useful than a proposal nobody

## Phase 0 acceptance criterion (SPEC.md §21)

> *a new account signs in with Google, lands as a Previewer, sees a
> token-styled empty state whose text comes from the registry, and
> `npm run seed -- --stops 1000` produces a usable dataset.*

Verified for real, not just typechecked:

- **Google sign-in is wired**, guarded by env presence (see "What's
  stubbed" — no real Google credentials exist in this environment, so the
  actual OAuth round-trip couldn't be exercised, but the NextAuth
  plumbing, adapter, and session callback were).
- **Previewer landing renders** — confirmed against a live `next dev`
  server: `curl localhost:3901/` returns 200 with the real copy-registry
  text ("Find a service event near you") and real token-styled markup
  (`btn-primary` class present, tokens.css/components.css loaded).
- **`npm run seed -- --stops 1000` works** — run for real against a local
  Postgres 16 + PostGIS 3.4 instance (stood up in this sandbox
  specifically to test this migration and this script rather than
  hand-writing SQL blind). Also load-tested at 5,000 stops per §16.3: 2
  seconds, using batched `createMany` rather than one insert per row.

## What was built

### Schema (`packages/database/prisma/schema.prisma`)

Two migrations, both applied and verified against a real database:

**`20260805063000_five_role_migration_and_phase0_models`**
- `Role` enum: `ADMIN | USER` → `OWNER | ADMIN | COORDINATOR | VOLUNTEER | PREVIEWER`.
  Hand-written, not autogenerated — see the two bugs below.
- New models: `Organization`, `Membership`, `Event`, `Household`, `Stop`,
  `UiCopy`, `AuditLog`.
- New enums: `EventKind`, `EventStatus`, `StopSource`, `StopStatus`.
- `postgresqlExtensions` preview feature + `extensions = [postgis]` on the
  datasource, so `ST_DWithin`/`ST_Contains` raw SQL is available once
  Phase 2/6 need it.

**`20260805063500_nextauth_adapter_tables`**
- `User.emailVerified`, `User.image`; new `Account` and
  `VerificationToken` models — what NextAuth's `PrismaAdapter` requires
  for Google account linking and email magic links. Purely additive.

**Two real bugs found and fixed while generating the first migration**
(worth flagging because they'd have shipped silently as a blind
`prisma migrate dev` accept): Prisma's autogenerated diff (1) cast
`"role"::text::"Role_new"` directly, which errors on every existing `USER`
row because `'USER'` has no counterpart in the new enum, and (2) emitted
`ALTER TABLE "Membership" ...` inside the enum-swap transaction *before*
`CREATE TABLE "Membership"` runs later in the same file. Both fixed by
hand; see the comment block at the top of the first migration's `.sql`.
Proven, not just reasoned about: a `test_user` row with the old `USER`
role was inserted, the migration applied, and the row came out
`PREVIEWER` — the "safe direction" SPEC.md §3.1 asks for.

**Deliberately not added yet:** `Season`, `Subscription`,
`SubscriptionEvent`, `Signup`, `FormSchema`, `Territory`, `Route`,
`RouteAssignment`, `Visit`, `VolunteerAvailability`, `InviteKey`,
`KeyRedemption`, `Notification`. These belong to later phases; keeping
them out of this migration kept the one non-additive change (the `Role`
enum) isolated and easy to verify in isolation.

**One addition beyond SPEC.md's base `Stop` model:** `Stop.needsReview:
Boolean`. Not in the schema block SPEC.md §5.1 shows, but §8's
`FIELD_ADDED` row says a volunteer-added stop "lands as needsReview" —
that field doesn't exist anywhere else in the model, so it was added now
rather than as a Phase 7 migration.

### `packages/database/src/scoped/` — the query-helper pattern (SPEC.md §6)

Split into `membership.ts`, `households.ts`, `events.ts`, `stops.ts` (all
re-exported from `scoped/index.ts`, which `src/index.ts` re-exports —
consumers just `import { stopsForSession } from "@service-projects/database"`).

```ts
resolveMembership(session, eventId?): Promise<{ role: Role } | null>
requireOrgAccess(session, orgId): Promise<void>          // throws
isStaff(role): boolean
organizationsForSession(session): Promise<Organization[]>
householdsForSession(session, orgId): Promise<Household[]>
householdForSession(session, orgId, householdId): Promise<Household | null>
eventsForSession(session, orgId): Promise<Event[]>
eventForSession(session, orgId, eventId): Promise<Event | null>
stopsForSession(session, eventId): Promise<Stop[]>
```

`resolveMembership` is the one piece of real logic: OWNER/ADMIN are
treated as org-wide from the session's top-level `User.role` (no
Membership row required), everyone else needs an event-scoped
`Membership` — which is what makes "Volunteer on one event, Coordinator
on another" (SPEC.md §3.3) actually work instead of being blocked by a
single global role.

`stopsForSession`'s volunteer branch returns `[]` unconditionally right
now — not a bug, a documented placeholder: a volunteer can only see stops
on a route they're assigned to, and `Route`/`RouteAssignment` don't exist
until Phase 3. The real field-level redaction (`visibleTo: Role[]` from a
form `Field`, SPEC.md §7.2) also doesn't exist until the form builder
ships in Phase 1.

**The ESLint rule** (`packages/config/eslint-preset.js`) bans
`prisma.stop`, `prisma.signup`, `prisma.household`, `prisma.visit`
outside `packages/database/src/scoped/`. Verified it actually fires, not
just written: a temporary `prisma.stop.findMany()` call was added to
`apps/rounds/src/app/page.tsx`, `next lint` failed with the rule's exact
message, then the line was removed and lint passed clean again. Wiring it
in required switching from `.eslintrc.json`'s `extends` (which couldn't
resolve `@service-projects/config/eslint-preset` through `next lint`'s
bundled ESLint resolver in this monorepo — a real, reproducible failure,
not a guess) to `.eslintrc.js` with a plain relative `require()`. Applied
to both `apps/rounds` and `apps/route-assignments`.

**Known gap, stated plainly:** this is a syntactic rule with no type
information. `import { prisma as db }` then `db.stop.findMany()` would
not be caught. A type-aware version is real added scope beyond what
SPEC.md §6 asked for, so it wasn't built — flagging it here so it isn't
mistaken for an oversight later.

### `packages/core-auth/` — permissions, requireRole, providers

- **`permissions.ts`** — the SPEC.md §15 matrix as data (`PERMISSIONS:
  Capability[]`), plus `can(role, capabilityId)` and `capabilityCard(role)`.
  Nothing consumes `capabilityCard` yet (the onboarding tour is Phase 5),
  but it's real and ready.
- **`requireRole(session, roles, { eventId? })`** — now **async**
  (needed for the event-scoped Membership lookup). Single-role call sites
  keep working (`requireRole(session, "ADMIN")`), but need an `await`
  added — done for the one real call site,
  `apps/route-assignments/src/app/admin/page.tsx`.
- **`authOptions`** — `GoogleProvider` and `EmailProvider` are only
  registered when their env vars are present, so an environment without
  real keys (like this one) still boots instead of shipping a broken
  "Sign in with Google" button. `EmailProvider`'s send step calls
  Resend's HTTP API directly via `fetch` rather than adding the `resend`
  SDK dependency for one POST request. `PrismaAdapter` wired in — no
  `Session` table added, since both apps use the `"jwt"` strategy and
  NextAuth never calls the adapter's session methods under that strategy.

### `apps/rounds/` — scaffold + copy registry + Previewer shell

Copied the shape of `apps/route-assignments` (package.json, tsconfig,
next.config, vercel.json) rather than reinventing it. New pieces:

- **`src/copy/`** — `en.ts` (flat dotted-key defaults),
  `t.ts` (`{{var}}` interpolation + a minimal ICU-plural subset:
  `{count, plural, one {# stop} other {# stops}}`), `createT(overrides)`
  ready to be fed org/event `UiCopy` rows once the copy editor
  (Phase 8) exists — nothing does yet, so `t` is `createT()` with no
  overrides, i.e. defaults only.
- **`scripts/check-copy-keys.mjs`** — the CI check SPEC.md §11.1 asks
  for. Regex-scans `src/` for every literal `t('key')` call and fails if
  `en.ts` has no default for it. Wired into `.github/workflows/ci.yml`.
- **`src/app/page.tsx`** — the entire Previewer experience right now:
  signed-out shows a landing hero with a sign-in button; signed-in shows
  the empty state ("No events published yet") in a real `Card` + `Badge`
  from `@service-projects/ui`. There's no key redemption yet (Phase 5),
  so this genuinely is the whole thing, not a cut corner.
- **`src/config/brand.ts`** — the one place to rename the app, per
  SPEC.md's cover page.

### CI

`.github/workflows/ci.yml` — didn't exist before. Runs against a real
`postgis/postgis:16-3.4` service container (plain `postgres` would fail
Rounds' migration, which enables the postgis extension), then
`migrate deploy`, `check:copy`, `lint`, `build`.

### Seed script (`packages/database/prisma/seed.mjs`)

Plain Node ESM against the generated Prisma client — no `ts-node`/`tsx`
dependency for a script that only ever runs via `node`. `@faker-js/faker`
is a devDependency, never imported by app code, zero production bundle
cost.

Generates households + stops inside real approximate bounding boxes for
Sandy, Draper, White City, and Cottonwood Heights (the areas SPEC.md
§22.1's locked decisions name as the actual service area). Uses batched
`createMany` with client-generated ids rather than one `create()` per
row — 5,000 stops seeds in about 2 seconds. Re-running wipes the
previous seeded org's event/stops/households first, so repeated runs
don't accumulate duplicates.

Verified against a live database, not just "it typechecks": ran at 100,
then 5,000 (timed), then left at 1,000 as the standing dev dataset.
Row counts, coordinate ranges, and sample addresses were all queried back
and checked by hand.

## What's stubbed / not real yet

- **No real Google/Resend/Stripe/Twilio/UGRC credentials exist in this
  environment.** Everything that depends on them is wired correctly and
  guarded to fail closed (missing keys ⇒ provider not registered, not a
  crash), but the actual external round-trip was never exercised. See
  `docs/rounds/OPEN-QUESTIONS.md`.
- **Volunteer stop visibility** (`stopsForSession`'s VOLUNTEER branch)
  returns `[]` unconditionally — correct today, but a placeholder for the
  route-assignment-based filter Phase 3 needs.
- **`resolveMembership`/`requireOrgAccess` treat OWNER/ADMIN as
  automatically having access to every org**, skipping a Membership
  lookup for them. Fine for a single-organization deployment (which is
  this app's actual real-world scope per SPEC.md §22.1), wrong the
  moment a second, unrelated org exists in the same database.
- **The ESLint ban is syntactic**, not type-aware (see above).
- **`t()`'s org/event override path** (`createT(overrides)`) is built
  but nothing calls it with real data — there's no admin UI or loader
  wired to `UiCopy` yet. Correct for Phase 0; flagging so "the copy
  registry supports overrides" isn't overstated.
